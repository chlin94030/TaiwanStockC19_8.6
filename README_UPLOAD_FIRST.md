# Alpha Radar V19.8.6 — 凍結最佳化候選＋不同時間點交叉確認

V19.8.6 依既有 S4（100檔×12日期）與最新 S6（150檔×18日期）結果做**跨規模穩健性篩選**，不是把同一批歷史資料反覆調到正報酬。候選只從 V19.8 早已存在的小型固定假說家族中選擇，主準則為：

1. 最大化 S4、S6 兩階段中「較差階段」的 bootstrap 90% 超額報酬下緣；
2. 若接近，再比較較差階段的平均超額報酬；
3. 不連續搜尋任意權重，不把缺資料因子補 0。

## 凍結候選權重

| 週期 | V19.8.6 凍結候選 | 治理狀態 |
|---|---|---|
| 5日 | `p197_annual_high = 100%` | 實驗性前瞻追蹤；尚未通過新時間點確認 |
| 20日 | `p197_annual_high = 100%` | 主要前瞻候選；目前三週期中證據最一致 |
| 60日 | `p197_liquidity = 70%` + `p197_annual_high = 30%` | 次要候選；S6較強但存在時間集中性 |

另保留既有、事前定義的市場風控：`CAUTION -> CASH`。這是「不進場」風控，不當成選股因子，也不代表市場下跌預測。

**重要：這些權重是 exposed development replay 後凍結的候選，不是全球最佳解，也不是新的獨立盲測，更不是自動下單授權。** 正式 `guarded` 路徑仍維持現金；`adaptive`／研究排名會追蹤凍結候選，供後續新證據驗證。

## 為什麼不是繼續調權直到更漂亮

最新 S6 已完成 150檔×18日期研究，但資料本身也明示這些日期可重疊、不是獨立試驗，而且基本面／法人等選配因子覆蓋仍為 0。因此 V19.8.6 不用同一批資料再做無限制參數搜尋，而是先把候選凍結，再移到不同時間點檢查。

## S7：真正要做的下一步

S7 維持 **150檔**，不再放大股票數，只改時間抽樣：

- 24 個基準日
- seed `271828`
- `stratified` 分段抽樣
- **排除 S4＋S6 已用過的所有精確基準日**
- 仍只使用價量／可追溯因子，不同時加入新資料源

這樣可以檢查候選是否只是剛好適合原先日期。S7 仍屬同一歷史期間的交叉確認，不冒稱真正未來 holdout；真正的 forward evidence 仍要靠凍結後的新交易日期逐步累積。

S7 的核心確認規則不會再重新調權：20日與60日候選都必須同時滿足平均超額 > 0、bootstrap 90% 下緣 > 0、leave-one-out 最差平均超額 > 0、前半與後半皆 > 0，且不能與 S4/S6 精確基準日重複。5日因目前證據較弱，獨立列為實驗性，不綁架20/60日核心候選。

## 升級方式

完整包維持 **100 個根目錄檔案**。若目前就是 V19.8.5，可直接使用 V19.8.6 Patch 覆蓋同名檔案；不確定版本則使用完整包。

保留既有 `data/`、Streamlit Secrets 與快取。Streamlit 入口仍是 `app.py`。為避免 Patch 新增根目錄檔案，Cloud Guide／QA 的實體檔名沿用 V19.8.5 名稱，但檔內版本與內容已更新為 V19.8.6。

S6 已有 150檔快取時，進到 S7 **先按 B「用快取執行本階段驗證」**；只有完整度不足時才按 A 補資料，不需要重抓相同150檔。
